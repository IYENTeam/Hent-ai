# Release Process

Hent-ai releases are repository metadata only: an immutable annotated tag and a
GitHub release. The Release workflow does not deploy production, restart an
OpenClaw gateway, or consume production secrets.

## Permanent branches and merge methods

- `dev` is the permanent integration branch. Short-lived feature and fix
  branches normally target `dev` and use squash merge.
- `release` is the permanent stabilization branch. Promote `dev` to `release`
  with a merge commit. Every pull request into `release`, including a reviewed
  `fix/rc-*` branch, uses a merge commit.
- `main` is the permanent releasable branch. Promote `release` to `main` with a
  merge commit so the release boundary and exact candidate ancestry remain
  visible. Every pull request into `main`, including a `hotfix/*` branch, uses a
  merge commit.
- Back-sync PRs (`main` to `release`, then `release` to `dev`) use merge commits
  so already-reviewed fixes retain their ancestry. Rebase merging is not used;
  it stays disabled so promotion and back-sync ancestry cannot be flattened
  accidentally.
- Every merge is human-only. Agents and workflows may open or validate pull
  requests, but they never merge them.

Before promotion, update `openclaw/package.json` to the intended
`YYYY.M.PATCH` version in its own reviewed change. A release dispatch must use
that exact value and the current `main` commit.

## Release candidates and hotfixes

For an RC, merge `dev` into the permanent `release` branch, stabilize it with
reviewed, merge-committed `fix/rc-*` pull requests, and merge the approved
`release` candidate to `main`. After promotion, back-sync `release` into `dev` so
RC-only fixes are not lost. The trusted Release workflow only publishes the
final package version from `main`; it does not publish an RC tag from another
branch.

For a hotfix, branch from `main`, open a merge-commit pull request back to
`main`, and use a new patch version. Immediately after the human merge,
back-sync `main` into `release`, then `release` into `dev`, through
human-reviewed pull requests before accepting unrelated release work. Never
reuse or move the previous version tag.

## Trusted workflow

1. Open the `Release` workflow on GitHub and choose `main`. Release authority is
   hard-pinned to `refs/heads/main`; changing the repository's default branch does
   not authorize another branch. A dispatch from any other ref fails before
   checkout or metadata inspection.
2. Enter the version from `openclaw/package.json`.
3. Leave `dry_run` enabled (the default) for the first dispatch. This validates
   current-main metadata, installs locked dependencies, and runs every lane from
   `node scripts/release-gate.mjs` without a tag or release write.
4. Review the dry-run result, then dispatch the same version with `dry_run`
   disabled. Only the publish job receives `contents: write`.

The version input is accepted only as `YYYY.M.PATCH` and is passed as inert data,
never evaluated as shell code. Release notes are generated by GitHub rather than
executing user-supplied text. Per-version concurrency is non-cancelling. If a run
is interrupted after its annotated tag is pushed, rerunning resumes GitHub
release creation; an existing same-SHA release is a no-op. A tag at another SHA
fails closed and is never force-moved.

A dirty operator worktree cannot affect the workflow because the workflow uses
the dispatched `main` SHA in a fresh checkout. Local dry-runs are advisory; the
trusted workflow is authoritative.

## Smoke check and rollback

After publication, verify that both surfaces resolve to the dispatched SHA:

```bash
TAG=vYYYY.M.PATCH
git fetch origin --tags
git rev-parse "$TAG^{commit}"
gh release view "$TAG" --repo IYENTeam/Hent-ai --json tagName,url,isDraft,isPrerelease
```

Compare `git rev-parse "$TAG^{commit}"` with the published workflow SHA, then
perform the service/plugin smoke checks appropriate to the separate deployment.
The release workflow itself never deploys or restarts a runtime.

Rollback means forward repair: revert the bad change on `main` through a human-
merged pull request, then back-sync `main` to `release` and `release` to `dev`
through human-reviewed merge commits. Increment the patch version and publish a
new tag only after all three permanent branches contain the revert. Do not
delete, recreate, or move an already published tag.

## Hardening integration

Long-running hardening branches can diverge far enough from `dev` that GitHub
cannot present a trustworthy conflict resolution. Integrate one through a fresh
short-lived branch created from the current `dev`, merge the exact reviewed
hardening head into it with a merge commit, and resolve conflicts deliberately.
Do not delete hardening-owned files merely because an older `dev` change deleted
their predecessors: verify the resulting import graph and restore every runtime
module and test still referenced by the integrated architecture.

Run `node scripts/release-gate.mjs` on the integrated tree before opening the PR.
The default local gate includes the external VisualAffectV2 corpus check and an
isolated local OpenClaw E2E run. GitHub's trusted release job runs the portable
nine-lane subset with `node scripts/release-gate.mjs --ci`; that CI mode does not
replace the local host evidence. The reviewed integration PR targets `dev`, then
the ordinary `dev` to `release` and `release` to `main` promotion flow applies.
All branch updates and merges remain human-only.
